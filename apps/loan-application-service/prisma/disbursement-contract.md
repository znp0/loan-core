# Disbursement read API and writer contract

`GET /api/v1/loan-applications/{applicationId}/disbursement` runs in `loan-application-service`. It accepts a UUID and the existing `access_token` cookie. CUSTOMER can read only their own application's result; STAFF can read any application's result. ADMIN does not implicitly receive STAFF access. The endpoint never creates or retries transfers.

The response follows API Spec (full), STT 32, except that `destinationAccount.bankCode` is omitted by agreement. `destinationAccount` contains only `maskedAccountNumber` and `accountHolderName`. Account numbers expose their last four characters only when longer than four; shorter numbers are fully masked. Attempts are ordered by `attemptNumber` ascending. `loanId` is null unless status is SUCCEEDED. Amounts are integer VND and timestamps are ISO-8601.

Errors use `{ code, message, details }`: 400 VALIDATION_ERROR for an invalid UUID; 401 UNAUTHORIZED for missing/invalid authentication; 403 FORBIDDEN for a disallowed role or another customer's application; 404 APPLICATION_NOT_FOUND for a missing application; 404 DISBURSEMENT_NOT_FOUND for an accessible application with no disbursement. Ownership is checked before looking up disbursements.

## Shared database contract for the decision implementer

Apply `20261028000000_add_disbursements` through the service's normal deployment migration process before using the endpoint or writing disbursements. Generate the app-local Prisma client from the updated schema. This task supplies persistence and GET only; approval and transfer execution remain the decision implementation's responsibility.

`prisma.disbursement` stores one record per application:

| Field | Type / rule |
| --- | --- |
| id | UUID, generated by Prisma |
| applicationId | Unique UUID; references LoanApplication |
| amount | BigInt; 1 through 9007199254740991 VND |
| currency | DisbursementCurrency; VND only, default VND |
| accountNumber, accountHolderName | Required recipient snapshot strings |
| status | DisbursementStatus: PENDING (default), PROCESSING, SUCCEEDED, FAILED |
| loanId | Nullable UUID in repayment-service; no cross-database foreign key |
| createdAt | Timestamp with timezone; defaults to creation time |
| completedAt | Nullable timestamp with timezone; set on successful completion |

`prisma.disbursementAttempt` stores each completed transfer attempt:

| Field | Type / rule |
| --- | --- |
| id | UUID, generated by Prisma |
| disbursementId | UUID referencing Disbursement |
| attemptNumber | Positive integer; unique within the disbursement |
| status | DisbursementAttemptStatus: SUCCEEDED or FAILED |
| transactionReference | Nullable string |
| failureCode, failureMessage | Nullable strings; store customer-safe values only, never raw bank responses or account numbers |
| processedAt | Required timestamp with timezone |

Tables are `disbursements` and `disbursement_attempts`; mapped columns use snake_case. Foreign-key deletion is restricted to preserve records. SQL CHECK constraints enforce the amount range and positive attempt numbers. The SQL-only partial unique index `disbursement_attempts_one_success_key` allows at most one successful attempt per disbursement; preserve it when generating future migrations.

The writer copies the agreed amount and recipient account into the disbursement when it is created. GET reads this snapshot, not mutable application fields. The writer must save the final attempt and matching parent status atomically. On success, save the resulting loanId and completedAt; on failure, keep loanId and completedAt null. Parent/attempt consistency and cross-service loan creation belong to that writer; the database constraints do not implement orchestration or idempotency.

## Verification

`pnpm --filter loan-application-service test` runs HTTP tests using the real Nest application with an in-memory persistence boundary. To run migration constraint tests, set `DISBURSEMENT_TEST_DATABASE_URL` to a disposable PostgreSQL database on localhost whose name starts with `loan_core_test`. The test applies migrations in a random schema inside a transaction and rolls back at the end. It never reads the service's development connection URL. Without that explicit test URL, the persistence test is reported as skipped.
